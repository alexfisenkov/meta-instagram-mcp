# Публикация видео через student broker

Контур добавляет Instagram Reels, YouTube video, TikTok Direct Post и Pinterest video Pin. Код и синтетические проверки не подтверждают живой допуск приложения, OAuth пользователя или публикацию. YouTube сам классифицирует Shorts. Реальные публикации выполняются только из сохранённого подтверждённого намерения платформы.

## Включение и совместимость

Без `META_BROKER_PUBLISHING_MEDIA_ORIGIN` и `META_BROKER_PUBLISHING_MEDIA_PATH` новый контур выключен: прежние MCP catalog/capabilities, Meta vault и YouTube read-only endpoint сохраняют прежний контракт. При включении origin обязателен точный HTTPS origin, path — точный префикс `/api/v1/social/publishing/media/`. После префикса допускается только один непрозрачный сегмент. Другие origin, query, redirects и произвольные HTTP назначения отвергаются. Значения origin/path оператор берёт из настройки API; конфигурация не является разрешением публиковать.

`META_BROKER_PUBLISHING_CONFIG_FILE` указывает на отдельный приватный JSON с `version:1,products:[]`; пример — `student-publishing.config.example.json`. В каждой записи `product` равен `youtube`, `tiktok` либо `pinterest`, `clientIdEnv`/`clientSecretEnv` содержат имена переменных окружения, `admission` — `disabled`, `test` либо `live`, `testSubjects` — список допущенных субъектов. Отсутствующая пара credentials даёт `not_configured`, частичная пара — отказ запуска. Для Instagram используется существующий subject-bound grant с проверенными scopes и admission; owner token и companions не используются.

Callback paths: `/social/oauth/{youtube|tiktok|pinterest}/callback` на origin `META_BROKER_CALLBACK_URL`. Возврат — `/social` на platform origin. Обратный прокси должен направлять эти точные пути в student broker и исключать OAuth query и media leases из access/error logs. OAuth state одноразовый, живёт 10 минут, закрепляет subject, product, config fingerprint и, при upgrade, ожидаемый стабильный ресурс. Для Google проверяется issuer и PKCE S256. Список разрешённых auth URL формируется только сервером.

Запрошенные scopes:

- YouTube: `openid profile youtube.readonly youtube.upload` (Google scopes с полным официальным URI). Write consent — отдельный flow. Старое чтение допускает дополнительный `youtube.upload` в ответе обмена/refresh того же клиента; отдельный клиент не требуется кодом. Отмена нового flow не меняет read vault. Подтверждённые YouTube options обязательно содержат строковый `categoryId` в канонической десятичной форме (`^[1-9][0-9]{0,9}$`); он входит в targetHash и явно отправляется в `snippet.categoryId`. Значение по умолчанию интерфейса 22 пользователь видит до подтверждения; брокер скрытого значения не подставляет. `Context.limits` для YouTube содержит `maxTitleCharacters:100`, `maxCaptionBytes:5000` (UTF‑8), `forbidAngleBrackets:true`; предел описания не обозначается числом символов. Заголовок считается по Unicode code points, `<` и `>` запрещены в заголовке и описании. Pinterest сообщает `maxTitleCharacters:100` и `maxCaptionCharacters:800`.

Необязательный булев `youtube.options.containsSyntheticMedia` позволяет пользователю явно раскрыть реалистичный изменённый или синтетический материал. При наличии отправляется точное значение в `status.containsSyntheticMedia`, включая `false`; отсутствие поля сохраняется. Брокер не анализирует и не угадывает содержание. Поле входит в targetHash; совместимость фиксирует дополнительный `tests/fixtures/publishing-hash-fixture-synthetic-media.json`.
- TikTok: `user.info.basic,video.publish`. Идентичность — `open_id` из token и `/user/info`.
- Pinterest: `user_accounts:read,boards:read,pins:read,pins:write`. Идентичность — числовая строка `Account.id` из `/user_account`, никогда username.

Подтверждённый identity/read grant сохраняется при отказе в необязательном write scope. `canPublish` и capability `publish` зависят от фактических scopes. YouTube ресурсы объединяются по subject/product/native channel ID; `connectionId` существующего ресурса сохраняется. Upgrade с `connectionId` отвергает другой канал. Disconnect write grant сохраняет read grant и соседние каналы. Внешний revoke этой командой не выполняется и обозначается `not_attempted`.

## Хранение и выполнение

Подкаталог `publishing/` внутри внешнего broker state root содержит отдельный AES-GCM vault и writer lock. Новые продукты и provider checkpoints не записываются в старые Meta/YouTube vault. Ключ, процессный single-writer lock, CAS, fsync, atomic rename и отказ после неопределённого commit переиспользуются из StudentVault. Backup должен включать этот подкаталог; checkpoint URLs и credentials секретны. Не копируйте vault в staging.

`social_connections_catalog/list/begin/disconnect` обслуживают подключения. `social_publish_context/submit/status/resume/cancel` используют существующий signed subject transport. Submit связывает tenant, subject, deliveryId, intentId, intentHash, targetHash и connectionId. Канонический JSON и SHA-256 проверяются по `tests/fixtures/publishing-hash-fixture.json`. Lease URL/expiry не входят в content identity. Повтор deliveryId с иным payload отвергается; две доставки одного batch не конфликтуют. Submit возвращает durable acceptance, не обещание успеха.

Runner обрабатывает не более двух доставок одновременно и не запускает параллельные шаги одного connection. Чанки продолжаются без 15-секундной processing-паузы: YouTube — на следующем tick, сохранённые legacy FILE_UPLOAD checkpoints TikTok — с коротким интервалом 3,1 секунды, чтобы оставлять запас для свежей creator-info проверки с документированным лимитом 20/min. Проверки processing выполняются через минуту для Instagram и через 15 секунд для остальных площадок; публичная модерация TikTok — раз в минуту. Processing ограничен 24 часами, затем требуется явная сверка через resume известной операции. Перед каждой новой внешней мутацией заново проверяются credentials, контекст и точные параметры, затем сохраняется `inFlight`. Read-only сверка уже принятой операции не блокируется изменившимся publish context: она использует действующие собственные credentials и точный provider checkpoint. Отзыв credentials и отключение connection остаются границами доступа.

Видео потоково сохраняется в `.media-cache/` внутри внешнего publishing state root, полностью проверяется по SHA/size и повторно используется всеми чанками delivery/source. Кэш приватный, имена выводятся только из UUID/role/SHA; произвольные файловые пути не принимаются. После перезапуска копия проверяется заново, при изменении inode/size/mtime/ctime выполняется повторный hash. Повреждённая копия/симлинк удаляются только внутри cache namespace; для повторного получения нужен действительный lease того же исходника. Копия, проверенная до истечения lease, остаётся допустима для незаконченного binary upload; URL ingestion Instagram и cover URL Pinterest требуют живой first-party lease непосредственно перед новой мутацией; при уже завершённом ingestion чтение исходника не выполняется. Удаление после подтверждённого ingestion/terminal и LRU eviction затрагивает только эти копии; оригиналы платформы не удаляются. Одновременно используемая копия защищена от eviction. Общий byte budget равен двум техническим maxBytes исходника (в стандартной runtime конфигурации — 40 GB); при нехватке места среди неиспользуемых копий возвращается ограниченный retryable отказ. Незавершённые temp-файлы убираются после рестарта, orphan/terminal cache — при восстановлении. Кэш не является резервной копией и не нужен в backup vault. HTTP provider запрос ограничен 20 секундами, исходник — 120 секундами; видео не передаётся через JSON/base64. В vault по-прежнему до 10000 доставок и 20 MB метаданных: дальнейшая retention/архивация требует отдельного регламента.

Instagram: container → status → publish → ID/owner/Reels readback. YouTube: resumable session → status probe → upload chunks → processing/owner/privacy/madeForKids readback; отдельная выбранная обложка отправляется в thumbnails.set для известного video ID. TikTok: fresh creator info (accountLabel из актуального creator_nickname)/privacy/interactions → explicit consent/disclosures → `PULL_FROM_URL` init с точной живой first-party lease → known publish_id status. Оригинал уже хранится на сервере LMS, поэтому новые TikTok deliveries не скачивают его в Node, не создают byte spool и не отправляют FILE_UPLOAD/PUT. Внешний TikTok сам получает исходник по выданной URL. Перед init повторно проверяются узкий HTTPS origin/path, отсутствие redirects/query/userinfo и срок lease; SHA/size исходника подтверждает платформа и связывает неизменяемый intent. Меняющиеся URL/expiry и внутренний transport checkpoint не входят в content hash. `PUBLISH_COMPLETE` TikTok подтверждает, что материал размещён. Для непубличной цели успешная квитанция может не содержать `providerId` и permalink: идентификатор операции `publish_id` остаётся в закрытом checkpoint и не подставляется вместо post ID. Для публичной цели без `publicaly_available_post_id` сохраняется `processing/awaiting_moderation`: этот ID появляется только после одобрения модерацией, иногда через несколько часов. Выполняется только чтение известного publish_id раз в минуту, без обращения к истёкшей source lease и повторной передачи. После зафиксированного `PUBLISH_COMPLETE` даже регресс статуса не включает upload снова. Rolling budget текущего процесса адаптера — не более 30 status запросов за 60 секунд на access token; при исчерпании переносится nextPollAt, без повторной мутации. Публичные int64 post IDs сохраняются без округления. Pinterest: media registration → потоковый multipart S3 upload → media status → pin на выбранной доступной доске → ID/board readback. Отдельная обложка необязательна: используется `cover_image_key_frame_time` (по умолчанию 0 секунд).

TikTok требует `isAigc`, оба brand toggles, consent и явное подтверждение коммерческого disclosure с текущим `disclosureVersion`, когда выбран commercial toggle. `brandContentToggle` запрещён вместе с `SELF_ONLY`; только продвижение собственного бренда этого ограничения не включает. Состояние приложения, аудит и владение media-domain/URL prefix в TikTok Manage URL properties оператор проверяет отдельно. Локальная конфигурация origin и App Production Draft не подтверждают эту внешнюю проверку. `url_ownership_unverified` возвращается как фиксированный provider reason без raw сообщения; подтверждённый отказ init допускает только явный retry, а потерянный/противоречивый ответ остаётся unknown и не создаёт новую публикацию. Для unaudited API клиента все публикующие аккаунты должны быть private на момент публикации, допустима только видимость `SELF_ONLY`, а пользоваться публикацией могут не более пяти пользователей за 24 часа. Это разные требования к аккаунту, материалу и приложению; код не меняет приватность аккаунта и не подставляет публичную видимость автоматически. Здесь фиксируются документированные ограничения, без новых предполагаемых approval gates.

## Восстановление и пределы доказательств

Status никогда не повторяет мутацию. Resume требует expectedVersion, при необходимости принимает новые asset/cover leases только с прежними id/SHA/size/mime. Для доказанного отказа до мутации либо точного provider отказа init без operation ID допустим явный retry. Неизвестный publish не создаётся заново: известная YouTube session сначала опрашивается, TikTok publish_id и Pinterest media_id сверяются до обращения к исходнику. Если байты уже приняты, истёкшая media lease не препятствует сверке; для недостающих байтов берётся потоково проверенный исходник. Pinterest после resume выбирает потребность в байтах по checkpoint/status media, независимо от текущей UI-метки stage. Только сохранённые legacy FILE_UPLOAD checkpoints TikTok могут продолжать известную операцию: сначала status, затем при необходимости недостающие проверенные байты; новый FILE_UPLOAD init не создаётся. Для этих checkpoints по-прежнему разрешены только два документированных upload host: `open-upload.tiktokapis.com` и `upload.us.tiktokapis.com`, HTTPS `/video/` с ограниченными upload query keys, без wildcard и redirects. Потерянный ответ создания Instagram container/TikTok init/YouTube session или публикации Instagram/Pinterest без recoverable ID требует ручной сверки; новый post автоматически не создаётся. Cancel прекращает только будущие локальные шаги, не удаляет внешние объекты и не допускается во время выполняющегося шага, после получения ID созданной публикации или после принятого TikTok PULL_FROM_URL init, полной передачи legacy TikTok-видео либо подтверждения `PUBLISH_COMPLETE`. Локальный cancel не вызывает TikTok remote abort и не выдаёт остановку загрузки за подтверждённый факт. Уже выданная provider lease должна оставаться доступной до подтверждённого terminal/cancel результата; один batch cancel request её не отзывает.

Проверки: `npm run typecheck`, `npm test`, `npm run build`; затем `npx vitest run --config tests/student-publishing.compiled.config.mjs` повторяет те же поведенческие fixtures через собранные модули и настоящий HTTP/MCP transport. Адресные tests/student-publishing* покрывают flow четырёх площадок, restart/unknown, смену payload, cross-owner, обновление lease, запрет redirects/corrupt streams, scope upgrade и совместимость прежнего MCP. UI-приёмка и реальные публикации этими тестами не подтверждаются; UI проверяется на staging с вымышленными аккаунтами. Автоматическое тестирование production UI и реальные посты не выполнялись.

## Offline purge publishing-субъекта

`purgePublishingSubject(directory,key,subject)` в `src/student/publishing-purge.ts` — helper отдельного publishing namespace для общего offline purge. Перед вызовом сервис останавливают: helper получает тот же StudentVault writer lock и не обходит занятый/оставшийся lock. Ключ и субъект проверяются до удаления. Если optional `publishing/` отсутствует, возвращаются нулевые legacy counts без создания папки или vault.

Операция ограничивает обход 30000 entries (можно только уменьшить maxEntries), проверяет закрытый vault, собирает план принадлежащих delivery/source cache/temp copies и не следует симлинку cache-directory. Сначала удаляются только копии из собственного publishing/cache namespace; затем одной vault transaction удаляются connections с inline credentials, OAuth states, deliveries/checkpoints и generation keys точного tenant/sub. При filesystem ошибке зашифрованные записи ещё сохранены, поэтому повтор может снова установить принадлежность оставшихся копий. Повтор после успеха идемпотентен. Неоднозначный старый temp source ID, одновременно используемый другим субъектом, отклоняется до удаления записей.

Типизированный отчёт содержит legacy `connections,grants,events,states,generations` и дополнительные `deliveries,mediaCacheFiles` для существующего namespace. Отдельных grant/event rows в publishing store нет; секреты удаляются вместе с connection, а эти два счётчика равны нулю. Отчёт не содержит идентификаторов, путей, URL или credentials. API/platform originals, данные других субъектов и внешние provider grants эта операция не удаляет. Общий CLI seam Meta/YouTube/read-connections/publishing собирается отдельно; сам helper не запускает CLI или сеть.


### Общая offline-точка удаления

Внешний CLI `src/student/purge-subject.ts --subject <проверенный-субъект> --confirm-purge` вызывает helper публикаций вместе с очисткой Meta, YouTube и отдельного read-account хранилища. Главный writer lock сервиса удерживается от начала до конца; существующие optional vault проверяются и расшифровываются под своими замками до первой записи. Для standalone publishing-helper его замок передаётся после preflight при удерживаемом главном замке, поэтому обычный брокер не может перезапуститься посередине процедуры.

Сначала очищается publishing namespace, затем остальные хранилища. Успех выдаёт только суммы legacy counters, а при наличии publishing — ещё `deliveries` и `mediaCacheFiles`. Inline credentials входят в число connections; отдельные grants отражают только хранилища, где grant — самостоятельная запись. При отказе после начала очистки возвращается `purge_incomplete` без успешных counts. Это не общий rollback нескольких файлов: сервис оставляют остановленным, проверяют состояние и повторяют процедуру для того же субъекта. Исходные видео/обложки платформы и опубликованные материалы провайдеров не удаляются; внешнее согласие и данные платформы остаются отдельными операциями. Новая retention или фоновая очистка в этой интеграции не добавлялась.
