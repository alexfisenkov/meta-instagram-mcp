# Возможности и границы готовности

Runtime factory сохраняет legacy API tools и регистрирует общие layered read/triage/analysis и guarded action tools для stdio и Streamable HTTP. Capability report показывает runtime status, а не доказательство входа в аккаунт или production readiness. Fake tests и наличие исходников не подтверждают live Meta/browser/phone доступ.

Cloud allowlist управляется отдельно от этого runtime: утверждённый контракт — 19 entries, то есть прежние 18 плюс named exception `meta_read_source`; `meta_capabilities` уже находился в cloud allowlist. Данный source tree не подтверждает, что приватное обновление gateway развернуто или что его текущий tool list совпадает с контрактом. Остальные layered/mutation tools не включены этим исключением; write/auth/stateful resolver operations остаются закрыты. Cloud `meta_read_source` разрешает шесть read operations: `account.inspect`, `inbox.list`, `conversation.read`, `comments.list`, `comments.replies` и `insights.read`. Его `readOnlyHint: false` сохраняет честное предупреждение, что UI conversation read может вернуть side effect `may_mark_seen`; sends, replies, reactions и иные writes не разрешены.

`meta_capabilities` отделяет общий статус источников от per-operation статуса. Общая строка browser может отражать самый свежий bridge, даже если он ещё не подтвердил аккаунт; per-operation status выбирает ready bridge с нужной live capability, когда такой есть. Ни один status запрос не открывает UI и не запускает `account.inspect`. Во время конкретного чтения browser provider может bounded-порядком проверить максимум три fresh bridge одного account binding, если они объявили и `account.inspect`, и запрошенную read capability. После owner verification выбранный bridge закрепляется до конца этого чтения. Поэтому summary/status и результат отдельного read могут различаться; для выполненной операции authoritative её observation/source provenance. Явная browser row reference всегда остаётся закреплённой за исходным bridge.

## Чтение, coverage и история

Каждое observation сохраняет source, coverage и полноту истории. API/браузер/телефон не объединяются по похожему имени или тексту: связать данные можно только по проверенному native ID либо явной ссылке владельца. `unread` означает состояние уведомления, `unanswered` — отсутствие ответа; одно не подменяет другое. Если направление, identity или история не подтверждены, статус остаётся `unknown`/`partial`.

`meta_capabilities` показывает snapshot readiness, а не выполняет UI-проверку. Общий статус browser может отражать самый свежий heartbeat неготового companion, тогда как операция читает наиболее свежий уже-ready bridge с нужной capability. Если для конкретного чтения готового browser bridge нет, активный read может выполнить bounded `account.inspect` максимум у трёх свежих browser bridges того же account binding, которые объявили и `account.inspect`, и запрошенную read capability. Следующие источники сохраняют свою очередь API → browser → phone; выбранный после owner verification bridge закрепляется до конца этого чтения. Проверка не запускается в фоне. Явный browser inbox-row ref остаётся закреплённым за своим bridge и никогда не переназначается. Поэтому общий capability status и результат отдельной операции могут различаться; для фактически выполненного чтения authoritative именно его observation/source provenance.

`meta_read_inbox` и `meta_triage_inbox` читают Direct через router API → browser → phone. Если для unpinned browser read нет ready bridge, операция может адресно выполнить `account.inspect` на нескольких свежих browser bridge того же binding, но только если каждый объявил проверку аккаунта и нужную read capability. До трёх кандидатов проверяются последовательно в оставшемся общем deadline; первый bridge, подтвердивший owner identity и live capability, закрепляется для самого чтения. Неудачная проверка одного bridge не делает другой аккаунт допустимым, а явная row reference не переходит на иной bridge. Если профильный URL и `nav` не дают handle, browser использует только уникальную видимую avatar-ссылку вне предков `nav`, `header`, `aside` и `main`; `aria-label` и `title` у неё отсутствуют, handle должен совпасть в href и `img alt`. После клика именно по найденной DOM-ссылке проверяются expected profile path и единственный настоящий `/accounts/edit/` control с текстом `Редактировать профиль` в header, затем восстанавливается исходный same-tab URL. Недостаток маркера, неоднозначность, несовпадающий аккаунт или невосстановленный URL завершаются `needs_selection`. Проверка не выполняет вход и не переносит cookies. Account verification и inbox read остаются отдельными результатами; `account.inspect` как самостоятельный вызов возвращает результат одного проверенного bridge и не делает отдельный повторный inspect после успеха.

Если read-only `account.inspect` или `inbox.list` не находит Instagram-вкладку в назначенном Chrome profile, extension может один раз создать неактивную вкладку с фиксированным `https://www.instagram.com/direct/inbox/` и ждать её загрузки только до общего task deadline. Она не создаётся для записи, conversation target, heartbeat или при нескольких подходящих вкладках. После открытия Content Script заново проверяет owner identity; экран входа, challenge и неизвестная UI остаются `needs_selection`/`unsupported_ui_version`, без автоматической авторизации.

На Inbox и на проверенном Direct thread route browser возвращает распознанные sidebar row cards с ограниченным видимым preview (максимум 600 символов) и короткоживущим `threadRef.explicitOwnerRef`, привязанным к точному DOM элементу, документу, verified account и bridge/tab. `unread` и `unanswered` остаются `unknown`, если UI не показывает точный маркер. Такой browser-only ref используется только с `meta_read_source(operation="conversation.read")`: router не отправляет его в API или phone, provider повторно выбирает исходный bridge, а worker разрешает только сохранённую вкладку. Новый thread route считается доказанным только после фактического перехода с текущего route; прежний thread URL не подтверждает клик по другой карточке. Уже открытая строка допускает повторное bounded чтение без клика только при сохранённой связи того же DOM-узла, документа, аккаунта и thread. Новый inbox list заменяет registry refs; доказанная связь может сохраниться лишь для той же подключённой строки на том же thread route, остальные refs нужно взять из нового snapshot. Перезапуск core, extension или content script теряет refs. Один лишь native thread ID или URL не доказывает, что видимые message/event nodes принадлежат выбранной переписке. Конкурентный UI operation отклоняется с `browser_ui_busy`, без очереди и повтора. Возможный `may_mark_seen` отмечается. Ref не является Instagram ID и не поддерживает send/reaction/write. В thread UI подходящие свежие видимые узлы могут возвращаться как `visibleEntries` с ограниченным текстом и `type: unknown`; это поле не отличает содержимое DM от системного или исторического события. Reader не назначает таким записям native ID, автора, направление или время. Если свежий текст не распознан, результат остаётся `unknown`, а не подтверждённо пустой перепиской. Selector miss, неоднозначная группа или задержка загрузки не доказывают пустой Direct.

`meta_triage_inbox` применяет API Direct unanswered-классификатор к ограниченному inbox page. Комментарии проверяются только для явно переданных `commentTargets` (не больше 20 точных media references); API использует подтверждённые sender IDs и bounded replies, а неполный ответный набор остаётся `unknown`. Browser/phone triage использует semantic `inbox.list`/`comments.list` операции и сохраняет их source/nativeRef. Одинаковый объект сводится между источниками только при совпадении account binding, канала и точного native ID; строка сохраняет все `sourceRefs`, а противоречащие статусы становятся `unknown`. Аналитика выбранных observations отдельно считает threads, messages, comments, replies и unknown answer status.

Graph API имеет ограничения доступа и окна чтения. API provider отдельно отображает scope/permission gates для inbox, conversation, comments/replies и insights. Ответы показывают per-source coverage; не считайте историю полной из-за одного успешного вызова. Browser поддерживает текущие semantic inbox/thread/comments/replies snapshots и bounded older-scroll operation для выбранного диалога. Inbox и comments pagination cursors не поддерживаются browser; запрос с таким cursor возвращает `unsupported_cursor`, а не первую страницу повторно. Phone явно отклоняет cursor операции; older-history scrolling не реализован. Cursor одного источника не преобразуется в cursor другого. Phone inbox без распознанных строк возвращает `coverage: unknown` с `inbox_rows_unrecognized`, а не подтверждает пустой Direct. Verified browser insights controls не обещаны. Phone поддерживает snapshots для inbox/thread/comments/replies/insights. UI conversation read может пометить диалог просмотренным, что отражается в side effects.

Для автоматического чтения router пробует API → browser → phone с одним общим deadline и сообщает tried/skipped sources, provenance, coverage, completeness и ошибки. По умолчанию deadline — 12 секунд на Linux/macOS и 50 секунд на Windows; Windows budget оставляет запас до стандартного 60-секундного MCP request timeout. Для API inbox triage часть оставшегося budget сохраняется для companion fallback. В Direct triage signal отменяет active Graph API GET и не допускает запуска следующих message GET; уже прочитанное сохраняется, а остальные conversations остаются `unanswered: unknown` при `coverage: partial`. Companion read task с истекшим бюджетом снимается из queued/leased состояния Hub; browser/phone companion проверяют expiry перед началом UI-работы. Если UI action уже начался, deadline не откатывает его и не гарантирует остановку. Этот cancellation contract не распространяется на Graph API comments/replies/insights GETs: общий provider context advisory, фактическая отмена поддерживается только отдельными операциями, где это явно указано. При `OUTCOME_UNKNOWN` запись не повторяется и source не меняется; сверяется тот же target тем же источником.

## Записи и подтверждения

MCP сначала готовит preview с точной source/account/target/context, fingerprint и request ID. Выполнение требует подтверждения, совпадающего preview и source-specific local gate. UI write дополнительно требует свежий signed grant от Hub, выданный после отдельного server-side approval. Browser allowlist содержит message send/react/unreact, comment reply/private reply и comment like/unlike при известном аккаунте и контексте; phone write controls ограничены message send/react/unreact, comment reply/private reply и comment like/unlike. API comment like/unlike unsupported, а Graph API reactions зависят от auth mode и могут быть unsupported. Hide/show/delete для comments не объявляются поддержанными текущим runtime. UI account/context checks и gates не означают Meta Access/permission или live UI pass. Timeout/неизвестный результат возвращает `OUTCOME_UNKNOWN`: автоматически не повторять и не менять источник; выполнить read-back того же target тем же source. `ACK`, read-back и доставка — разные доказательства.

Media publishing остаётся отдельной legacy API операцией и использует `META_INSTAGRAM_WRITE=true` вместе с `confirm:true`; подробности — в разделе [Публикация](../README.md#публикация).

Все четыре профиля, их prerequisites и текущие ограничения собраны в [инструкции установки](install.md).
