# Hosted Meta broker для пользовательских подключений

Отдельный `dist/student-server.js` обслуживает подключения разных пользователей. Legacy single-account stdio/HTTP runtime, его environment token и companions в этот процесс не подключаются. Запуск не публикует материалы, не отправляет сообщения и не меняет рекламу.

## Контракт платформы

Listener привязан к `127.0.0.1`; перед ним нужен управляемый TLS proxy. `/student/mcp` доступен только сервису платформы: `Authorization: Bearer <service-token>` и `X-Meta-Subject: <HS256-JWT>`. Подписанный subject выводит сама платформа из текущей сессии. Claims: `iss=masterskaya-platform`, `aud=meta-student-broker`, `tenantId=masterskaya`, внутренний `sub`, целые `iat/exp`, срок не больше 60 секунд. Будущее `iat`, истёкший JWT, чужие issuer/audience/tenant и повторные security headers отклоняются. Публичный браузер получает только DTO от платформы.

SDK Streamable HTTP поддерживает обычный MCP initialize, notifications, tools/list и tools/call. Для POST клиент отправляет `Content-Type: application/json` и `Accept: application/json, text/event-stream`. Каталог содержит ровно пять инструментов:

| Инструмент | Аргументы | Результат |
|---|---|---|
| `meta_connections_catalog` | `{}` | `products[]`: product, label, status, capabilities, reason? |
| `meta_connections_list` | `{}` | `connections[]`: id, product, status, account{id,label}, capabilities, updatedAt, reason? |
| `meta_connections_begin` | `{product}` | authorizationUrl, expiresAt |
| `meta_connections_disconnect` | `{connectionId}` | connection |
| `meta_connections_read` | `{connectionId,operation,limit?,cursor?,mediaId?}` | data, coverage, source, updatedAt, limitations |

Product: `instagram | facebook | messenger | threads | ads | whatsapp`. Operation: `account | posts | metrics | comments | inbox`. Connection id — UUID брокера; account id — отдельный native provider asset id. Tool schemas строгие: subject, token, произвольный Graph path, URL и дополнительные поля не принимаются. Комментарии читаются только после проверки mediaId в собственной коллекции выбранного asset; окно ограничено 1000 публикациями, за его пределами чтение закрывается. Provider URLs из paging не выдаются и не выполняются; используется только проверенный непрозрачный cursor.

## Конфигурация

`student-broker.config.example.json` — шаблон приватного реестра. Он содержит имена environment references, не credentials. Реальный файл и secret environment размещают вне checkout. `admission=disabled` по умолчанию. `test` допускает только перечисленные внутренние subject ids; остальные видят `review_required`. `live` устанавливает оператор после независимой проверки нужного App Review/Advanced Access и рабочего режима. Эта настройка описывает admission, а не доказывает свежий доступ Meta. Фактические capabilities связи выводятся из проверенного grant и обнаруженных assets.

Значение `configId: "0"` в шаблоне — заглушка оператора: до admission замените её на точный numeric configuration ID своего login setup. App IDs и secrets читаются только по названным env references. Threads требует свою пару Threads App ID/Secret, Unified — Meta App ID/Secret. Один JSON record соответствует одному продукту; config keys уникальны.

| Environment | Требование |
|---|---|
| `META_BROKER_SERVICE_TOKEN` | Независимый случайный service secret, минимум 32 символа. |
| `META_BROKER_SUBJECT_KEY` | Base64 ключ HS256, минимум 32 декодированных байта. Тот же ключ установлен в API платформы. |
| `META_BROKER_VAULT_KEY` | Другой base64 ключ, ровно 32 декодированных байта для AES-256-GCM. |
| `META_BROKER_STATE_DIR` | Абсолютный путь приватного состояния вне checkout/install tree. |
| `META_BROKER_PLATFORM_ORIGIN` | Единственный HTTPS origin платформы без завершающего `/`; возврат всегда `/social?meta=connected\|cancelled\|error`. |
| `META_BROKER_CALLBACK_URL` | Точный зарегистрированный HTTPS redirect URI; путь `/meta/oauth/callback` или `/student/oauth/callback`. |
| `META_BROKER_CONFIG_FILE` | Необязательный приватный JSON реестр. При отсутствии все продукты `not_configured`. |
| `META_BROKER_PORT` | Порт loopback, по умолчанию 8788. |
| `META_BROKER_REFRESH_INTERVAL_MS` | Интервал lifecycle scheduler: 1000–3600000 ms, по умолчанию 60000. |
| `META_BROKER_OPERATOR_NAME` | Название оператора для публичных legal pages; не встраивается в source tree. |
| `META_BROKER_PRIVACY_CONTACT` | Контактный email оператора. Если name или email отсутствуют, legal pages возвращают 503 `not_configured`. |

```sh
npm ci
npm run typecheck
npm test
npm run build
# Secrets доставляет service manager; команда не читает legacy .env.
node dist/student-server.js
```

Proxy пропускает только публичные callbacks на внутренние `/student/oauth/callback` и `/student/webhooks/<configKey>`. В upstream Host должен быть `127.0.0.1:<port>`. `/student/mcp` и `/health` остаются в доверенном сервисном контуре. GET `/health` возвращает ровно `{status:"ok"}` без авторизации и дополнительных полей: build/install probes сравнивают этот объект целиком. Отдельный GET `/student/diagnostics/callback-count` доступен только с loopback и точным service Bearer, без query и браузерного Origin; он возвращает только `{callbacksReceived:0}` и не публикуется gateway. `callbacksReceived` — насыщаемый на `Number.MAX_SAFE_INTEGER` счётчик GET callback после проверки Host/Origin, включая неизвестный state и отклонённые дубли параметров; POST не считается. Он хранится только в памяти процесса, обнуляется при перезапуске и не пишет строки журнала на каждый вход. Разность до/после попытки доказывает получение HTTP callback этим listener, а не успешную авторизацию; нулевой счётчик после перезапуска не описывает прошлые попытки. Это не доказательство live Meta access. Браузерные Origin на сервисном endpoint не допускаются. Access logs proxy должны скрывать query callback, OAuth code/state и verify token. Не публикуйте systemd environment, vault, cookies или provider payload.

GET `/privacy` и `/data-deletion` — публичные русские страницы с данными оператора из environment, HTML escaping, CSP, nosniff и no-store. При внешнем префиксе proxy отображает их на `/meta/privacy` и `/meta/data-deletion`. Это текстовые инструкции без формы и сохранения ввода; POST отклоняется. Удаление данных запрашивается по email и выполняется вручную после проверки принадлежности, без запроса паролей, токенов, паспорта или личной переписки. Страница не обещает автоматического удаления оригиналов в Meta или всех backup/third-party копий.

## OAuth и провайдеры

State содержит hash случайного 256-bit значения и привязку к subject/product/provider/config fingerprint/точному return target, действует десять минут и атомарно потребляется до обмена кода. Denial также потребляет state. Fingerprint включает только семантику OAuth grant: product/key/provider, app id/secret, config id, API version и callback. Изменение этих полей закрывает прежний grant/flow. Admission, test subject allowlist и webhook verify token не меняют identity grant; текущая admission policy заново проверяется при callback и read. Новый begin того же subject/product повышает generation и заменяет прежний pending flow, поэтому поздний старый callback не возвращает снятые assets. Disconnect также отменяет pending OAuth и блокирует уже начатый exchange.

Для распознанного state broker пишет в stderr одну JSON-строку `student_oauth_callback` с фиксированными `stage`, `product`, `outcome`, allowlisted `reason` и булевыми `hasCode`/`hasProviderError`. При ошибке Meta добавляются только числовые HTTP status, Meta code/subcode и одна из фиксированных категорий endpoint: `token_exchange`, `token_inspection`, `account_identity`, `asset_discovery` или `api_request`; Threads отдельно различает `token_short_exchange`, `token_long_exchange`, `app_token_exchange` и `token_refresh`. Аудит не содержит state, OAuth code, subject/account IDs, URL, заголовки, текст ответа или сообщения исключений. Невалидные и неизвестные state не журналируются. Поля не меняют redirect, доступ, grant или DTO платформы; при проблеме записи аудита callback продолжает обычный путь. Эти записи помогают локализовать сбой, но сами по себе не доказывают сохранённое подключение.

Google возвращает браузер на отдельный внешний `GET /youtube/oauth/callback` с `code`, одноразовым `state` и issuer `https://accounts.google.com`; для denial используется `error`. Callback route сверяет точный product redirect path и Google issuer до обмена. Брокер завершает поток HTTP 303 на platform `/social?youtube=connected`, `?youtube=cancelled` или `?youtube=error`; query-параметр отображает статус, а подключения UI перечитывает с сервера. Gateway должен сохранить `/youtube/oauth/callback` как upstream path и исключить callback query из access/error logs.

Успешный повторный consent в одной транзакции обновляет все подтверждённые assets выбранного subject/product и отключает отсутствующие в новом полном discovery. Их events удаляются; старый grant теряет credential, когда у него не осталось active assets. Другие продукты, субъекты и законные assets общего grant сохраняются.

| Продукт | Семейство и discovery | Доступное чтение |
|---|---|---|
| Instagram | `instagram_login` использует Instagram-hosted Login и отдельные credentials без `config_id`; short-lived code exchange на `api.instagram.com`, документированный long-lived exchange на `graph.instagram.com`, затем подтверждает OAuth `user_id` по `id` либо `user_id` единственного свежего `/me?fields=id,user_id,username`; ID ресурса берётся только из профессионального `user_id`. Фактически выданные `permissions` из code exchange задают возможности; создаётся один Instagram asset. `instagram_unified` сохраняет прежний Facebook-hosted BISU flow с `config_id`, SYSTEM_USER inspection и `/me/assigned_instagram_accounts` для нескольких assets. | Профиль/публикации, reach, комментарии и inbox metadata только при соответствующих фактически выданных permissions. Direct Instagram Login сейчас не обновляется автоматически: требуется повторная авторизация до истечения long-lived token. |
| Facebook Pages | `facebook_business`; USER `/me/accounts` с Page tokens или SYSTEM_USER `/me/assigned_pages`. Каждая Page проверяется своим credential. | Профиль/публикации; комментарии при дополнительном grant. |
| Messenger | `facebook_business`, те же Page identities с отдельным product config. | Профиль и metadata списка conversations при фактических messaging/metadata/engagement grants. |
| Threads | Собственная authorization и code exchange; long-lived upgrade и отдельный app-token inspection. | Профиль/посты; replies и фиксированный набор insights при фактических grants. |
| Meta Ads | `facebook_business`, `/me/adaccounts`; granular target scopes ограничивают account ids. | Профиль ad account и account insights за последние 30 дней. |
| WhatsApp Business | `facebook_business`, `/me/assigned_whatsapp_business_accounts`, затем WABA `/phone_numbers`. Phone и parent WABA сохраняются раздельно. | Профиль номера; только сохранённые подписанные входящие text webhook events при messaging grant. Исторического Cloud API inbox здесь нет. |
| YouTube | Отдельный Google Web OAuth adapter с одноразовым state, PKCE S256 и OIDC subject. Один grant открывает все обнаруженные через `channels.list(mine=true)` собственные каналы. Повторный вход другой Google identity не отключает прежние каналы владельца. | Чтение выбранного канала: title, public custom URL и Data API channel counters `viewCount`, `subscriberCount`, `videoCount` с флагом `hiddenSubscriberCount`. Для ручного Facebook-hosted web OAuth code exchange (Instagram Unified/BISU и Facebook-based products) повторно передаётся тот же `redirect_uri`, что и в authorization URL. Direct Instagram Login использует собственный Instagram-hosted authorize URL и POST с form-data на `https://api.instagram.com/oauth/access_token`, где передаётся тот же `redirect_uri`, затем long-lived exchange на `https://graph.instagram.com/access_token`. Запросы Graph API идут на `https://graph.instagram.com/<configured-version>`. Источники: [Instagram Business Login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login) и [Instagram Login Get Started](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/get-started). Threads использует собственный POST code exchange.

Facebook-based provider flows inspect scopes through `debug_token` with `is_valid`, matching app_id, scope names, expiry and granular_scopes; requested scopes do not become granted scopes. Unified requires SYSTEM_USER and client_business_id. Direct Instagram Login accepts one explicit short grant: Meta's documented `data[0]` response or a top-level OAuth token response with the same required fields. A response containing both representations is rejected. Actual allowlisted `permissions` (CSV string or string array, at most 32 entries of 100 characters; CSV at most 4096 characters) and `instagram_business_basic` are required; requested scopes never become granted scopes. The provider upgrades the short token using `ig_exchange_token` and requests `/me?fields=id,user_id,username`. Exactly one flat profile or one object in `data` is accepted; mixed, empty or multiple profiles are rejected. OAuth `user_id` must match the fresh token profile’s app-scoped `id` or professional `user_id`; the canonical connection resource is always the required professional `user_id`, never an arbitrary `id` fallback. Account reads verify that professional resource again and expose only `user_id`/`username`. Numeric Instagram `id`/`user_id` JSON values preserve their original decimal digits using the JSON reviver source context on Node 22+; runtimes without that context accept only safe numeric integers and reject unsafe values instead of stringifying an already rounded number. Other provider identities, counts and lifetime values are not coerced. Bearer token type is case-insensitive per [RFC6749 §5.1](https://www.rfc-editor.org/rfc/rfc6749#section-5.1); other types, missing token fields and unsafe/expired lifetime values are rejected. Automatic refresh remains disabled until optional permissions can be re-verified. Configured API version is explicit and not inherited from the legacy runtime.

The callback audit has separate fixed reasons for absent/malformed short identity, invalid profile representation, absent/malformed profile identity, short response, permissions, long response, token type and expiry verification. These do not include response bodies, credentials or identifiers. A live generic `grant_verification_failed` alone does not establish which response representation or validation failed; compatibility tests do not prove the shape of a real provider response.

The broker emits the canonical five-parameter direct Instagram URL (`client_id`, `redirect_uri`, `response_type`, `state`, `scope`), preserving compatibility with an already installed platform during rollout and normal desktop session reuse. The broker does not infer the device or force a password prompt. A trusted platform can add `force_reauth=true` for mobile or explicit recovery, as recommended by [Meta’s 14 June 2025 changelog](https://developers.facebook.com/docs/instagram-platform/changelog/); its API/browser guards must allow only that exact value on the direct Instagram endpoint, preserving the original one-use state and callback. Deprecated `force_authentication` is not used. Current `enable_fb_login` controls only the Facebook login option and is left at Meta’s default. Profile fields and representations follow [Business Login](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login/) and [Get Started](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/get-started/); compatibility regressions do not establish a successful mobile/desktop provider flow.

Independent Direct Login authorizations retain the subject's previously connected Instagram accounts. Reconnecting the same account replaces that account's grant without duplicating its connection; another account remains connected with its own credential. The broker-generated authorization URL contains the single-use, subject/config-bound state; the App Dashboard example URL without that state is not a working broker connection link. Requested publishing permission prepares the authorized feature set; this broker's current tools still do not publish content.

YouTube authorization requests `openid profile` only to obtain the stable OIDC `sub`; the userinfo response is projected to `sub` only and email/profile fields are discarded. `youtube.readonly` is the only YouTube permission requested. The access and refresh tokens remain in the encrypted subject-bound vault at `<state-dir>/youtube/vault.json`, separate from the legacy Meta `<state-dir>/vault.json`. This lets an older Meta-only broker release reopen its unchanged vault after rollback without parsing YouTube records. The lifecycle refreshes an access token inside its five-minute expiry window, verifies the same OIDC subject and that `channels.list(mine=true)` still returns owned resources, and preserves a refresh token when Google does not rotate it. If a fresh code exchange returns no refresh token, it fails with fixed `youtube=refresh_required`; it creates no grant and leaves previous grants/channels and refresh credentials untouched. It never borrows an old account's refresh token for the new grant. An invalid/revoked refresh closes the grant to `reauth_required`; only the owner can start the replacement consent. Data API channel counts are lifetime/current channel fields, not period reports. `yt-analytics.readonly` and `reports.query` are outside this slice; no Analytics time series are exposed, and their denial cannot block channel access. The verified code paths follow Google's [Web Server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [OpenID Connect UserInfo](https://developers.google.com/identity/openid-connect/reference), [YouTube `channels.list`](https://developers.google.com/youtube/data/reference/rest/v3/channels/list), and [OAuth scopes](https://developers.google.com/identity/protocols/oauth2/scopes). Google Cloud must separately approve any required sensitive-scope access; code and credentials alone do not prove that approval.

Для Threads inspector получает отдельный app access token через официальный `client_credentials` GET `https://graph.threads.com/oauth/access_token` и использует именно выданный app token в Authorization для `debug_token`, включая проверку после refresh. Facebook-форма app id/secret с разделителем не используется для Threads: его собственный app credential имеет префикс `TH|`. App token также содержит секрет и остаётся только на сервере. Источник: [Threads App Access Tokens](https://developers.facebook.com/documentation/threads/get-started/app-access-tokens), обновление 18.08.2026.

Threads long-lived exchange и refresh передают `access_token` query-параметром только на закреплённый HTTPS host, как в [официальной документации](https://developers.facebook.com/docs/threads/get-started/long-lived-tokens/) и [образце Meta](https://github.com/fbsamples/threads_api/blob/main/src/index.js). URL и токены не входят в ошибки или аудит; redirect и retry по-прежнему запрещены. Это совместимость контракта, не доказанная причина какого-либо live Meta error.

Threads inspection следует [официальному debug_token контракту](https://developers.facebook.com/docs/threads/troubleshooting/debug-access-token/): документированный ответ не содержит `app_id`, а Meta проверяет принадлежность input token тому же приложению, чей access token использован для inspection. Брокер каждый раз получает свежий app token через выделенные Threads app ID/secret и передаёт именно полученный токен в GET inspection; environment token и имена приложений не служат доказательством. Без такого binding операция закрывается. Требуются `is_valid=true`, `type=USER`, строковый user_id, ограниченный фактический список Threads scopes с `threads_basic` и валидные сроки. Если `app_id` всё же передан, он должен точно совпасть; unsafe числовое значение не приводится к строке. При первом обмене user_id сверяется со свежим `/me`, при refresh — с сохранённым ожидаемым ID. Нулевой срок не считается бессрочностью: long-lived exchange/refresh остаётся отдельной конечной границей. Для не-Threads провайдеров `app_id` остаётся обязательным. Фиксированные `threads_*` reasons различают binding, app token, тип, scopes, identity и expiry без provider payload.

Conversation metadata для Instagram и Messenger запрашивает и возвращает только `id,updated_time`, подтверждённые [Messenger Conversations](https://developers.facebook.com/docs/messenger-platform/conversations/) и [Instagram Conversations](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/conversations-api/). Message count, текст и история не запрашиваются. Это минимальный контракт, а не доказательство работоспособности Inbox, доступа Advanced Access или причины конкретного live отказа.

Messenger отдельно получает Page access token через `GET /<page-id>?fields=id,name,access_token` с текущим подтверждённым USER/SYSTEM_USER grant, затем независимо сверяет `GET /me?fields=id,name` на полученном Page token с выбранным Page ID. Выдача `inbox` требует фактических scopes `pages_read_engagement`, `pages_messaging`, `pages_manage_metadata` с нужным granular target и подтверждённой задачи `MESSAGING` либо `MODERATE` из page discovery. Наличие scopes само по себе больше не включает Inbox. Источники: [Meta specific-page token](https://www.postman.com/meta/facebook/request/tass6hw/get-specific-page-access-token) и [Messenger Conversations](https://developers.facebook.com/docs/messenger-platform/conversations/).

Если Page token отсутствует или его выдача отклонена permission error, подтверждается только минимальный профиль `id,name` и сохраняется только capability `account`; Conversations не вызывается. Токен из списка страниц не принимается вместо отдельной выдачи. Несовпадение selected Page либо `/me` закрывает обмен до сохранения credentials. При Inbox read Page context проверяется заново; отсутствие отдельного Page token или совпадение с system/user grant отвергается до Conversations. Профиль при отсутствии Page token читает только выбранный `/<page-id>` минимальными полями, но system grant никогда не подставляется в Conversations.

Messenger использует новый fingerprint `messenger-page-auth-v1`: старые scopes-only grants и pending states требуют нового явного consent. Fingerprints Facebook, Instagram, Threads, Ads и WhatsApp не меняются. Facebook API сохраняет прежний путь; Google/owner credentials не используются. Подтверждённый Page token/tasks/scopes не доказывает App Review/Advanced Access или фактическую работоспособность Inbox: отдельный реальный read остаётся воротами приёмки.

После ошибки собственного разрешённого read runtime пишет только `student_connection_read_error`, фиксированные product/operation/reason и, если доступны, числовые HTTP status/Meta code/subcode. ID, subject, данные переписки, URL, exception message и credentials исключены. Отдельный optional read-audit sink не меняет существующий callback contract и не влияет на исход операции при отказе журнала. Неизвестная ошибка получает `read_failed`.

Meta 10/200 (`permission_unavailable`) снимает только отказавшую capability выбранного connection под проверкой текущего grant/credential; профиль и другие assets общего grant сохраняются. Отказ обязательного `account` identity read закрывает только выбранный connection (`identity_verification_unavailable`). Meta190/`reauth_required` и несовпадение проверенной личности по-прежнему закрывают весь соответствующий grant. Поздний отказ старого запроса не меняет replacement grant. Новые DTO reason: `operation_permission_unavailable` / `identity_verification_unavailable`; статусы и operation names не расширены. Ранее очищенные credentials автоматически не восстанавливаются, новый consent остаётся явным действием пользователя.

Точные fixed hosts: Facebook authorization `https://www.facebook.com/dialog/oauth`; direct Instagram Login authorization `https://www.instagram.com/oauth/authorize`, code exchange `https://api.instagram.com/oauth/access_token`, Graph `https://graph.instagram.com/<configured-version>`; Threads authorization `https://threads.com/oauth/authorize`, code exchange `https://graph.threads.com/oauth/access_token`. Long-lived Threads exchange/refresh — `https://graph.threads.com/access_token` и `/refresh_access_token`. Google authorization `https://accounts.google.com/o/oauth2/v2/auth`, token `https://oauth2.googleapis.com/token`, OIDC userinfo `https://openidconnect.googleapis.com/v1/userinfo`, YouTube Data API `https://www.googleapis.com/youtube/v3`. Direct Instagram refresh пока не поддержан. Facebook Graph — `https://graph.facebook.com/<configured-version>`. Ни caller, ни реестр не могут добавить произвольный host или URL. Redirect upstream запрещён; каждый request ограничен временем и размером ответа, без сетевого retry.

Одна exchange/read/refresh операция ограничена 32 provider requests и общим 30-секундным deadline; один HTTP request — максимум 8 секунд/1 MiB ответа. Discovery edge ограничен десятью страницами по 100 записей. Превышение закрывает операцию с явным error, не возвращает притворно полный набор assets.

## Credential lifecycle и хранение

Vault хранит отдельные grant, connection asset, OAuth state и webhook event records. Весь файл шифруется AES-256-GCM; credentials дополнительно шифруются с AAD tenant/subject/grant/provider. Ключ не хранится рядом с ciphertext. Каталог приватный, файл 0600 на POSIX; для Windows применяются существующие ACL-проверки. Приватные права временного файла устанавливаются и проверяются до записи ciphertext; отказ защиты не создаёт новую версию vault. Meta и YouTube используют отдельные vault-каталоги внутри state root: `<state-dir>/vault.json` и `<state-dir>/youtube/vault.json`, с независимыми lock-файлами. Один процесс сервиса держит оба exclusive writer lock; несколько replicas с тем же state root не поддерживаются. Внутри процесса транзакции сериализованы, перед записью проверяется ciphertext CAS, затем fsync/atomic rename.

Если rename уже изменил файл, а последующий directory fsync завершился ошибкой, операция сообщает `vault_commit_uncertain`: кандидат data/hash остаётся согласованным с собственным rename, но snapshot/reads и обычные writes закрываются. Следующий access-reducing disconnect допускается только после точного ciphertext CAS и снимает quarantine лишь после успешной durable записи. При несовпадении файла или повторной ошибке доступ остаётся закрыт. Не повторяйте OAuth/refresh как якобы несостоявшуюся операцию; проверьте filesystem и выполните безопасный disconnect либо offline purge. Такой отказ не означает, что rename не произошёл, и не даёт гарантии переживания аварийного отключения питания до исправления fsync.

Штатный SIGTERM закрывает listener, дожидается lifecycle и освобождает lock. После аварийного падения оставшийся `.writer-lock` сам не удаляется: оператор сначала доказывает, что старый процесс остановлен, сохраняет vault/key отдельно и снимает stale lock вручную. Копирование только vault без ключа не восстанавливает grant. Не удаляйте и не ротируйте ключ без отдельного recovery плана. Смена ключа не реализована; нужна контролируемая миграция.

Threads refresh выполняется до expiry, в семидневном окне и только после первых 24 часов жизни токена. Scheduler использует реальный expires_in/inspection expiry. Результат обновляет credential только при прежнем ciphertext, active grant и хотя бы одном active asset; завершившийся после disconnect/rotation refresh не восстанавливает доступ. BISU/SUAT не получает выдуманный 60-дневный срок или Facebook long-lived exchange. Неподдерживаемая refresh-схема требует reconnect. Invalid/expired/revoked grant переводит все связанные assets в `reauth_required`; invalid token не повторяется автоматически.

После Threads refresh заново проверяются app/user/scopes и data-access expiry: обновление срока самого токена не скрывает отдельное истечение permission grant. Потеря прежнего scope требует reconnect. Неопределённый исход refresh также закрывается для автоматического повтора (`refresh_outcome_unknown`); оператор/пользователь проходит новый consent, а старый credential не используется.

Facebook Login USER token проходит официальный `fb_exchange_token` upgrade до discovery, затем повторную app/user/grant inspection. Эта ветка никогда не применяется к Unified или SYSTEM_USER. Его дальнейший неподдержанный автоматический refresh не имитируется: фактический expiry требует нового consent.

Disconnect немедленно закрывает локальный доступ. При отключении одного из нескольких assets общий grant остаётся active; после последнего credential стирается логически из новой encrypted версии файла. Meta permission revoke, WABA subscription, signup/phone registration и удаление Meta данных — отдельные внешние операции; этот сервер их автоматически не делает. Старые backup ciphertext и уже отправленный provider request нельзя отозвать локальной записью; результат concurrent read перед выдачей дополнительно сверяется со статусом connection.

Политика истории: отключённая connection сохраняет subject, продукт, native account id/label и parent asset id при наличии, внутренние connection/grant ids, статус/reason и дату. Capabilities отключённой связи очищаются. После последнего active asset grant сохраняет только служебную связь/статус/дату; provider user/business id, scope set, expiry и credential очищаются. Эти метаданные нужны для отображения истории отключения и остаются до проверенного запроса на удаление; они не дают доступ к Meta. Запрос на полное удаление subject выполняется отдельной offline-процедурой ниже.

Webhook сначала проверяет подпись исходного body секретом конкретного config key, затем распределяет каждый entry только по активным собственным connection/grant и точному native asset. Смешанный batch не передаётся целиком одному пользователю. Для WhatsApp дополнительно совпадают WABA и phone_number_id. Дедупликация — по connection/message; поддерживаются только text message events, до 30 дней/10000 событий на vault. Подписка приложения на WABA требует отдельного разрешённого Meta setup; её наличие не предполагается.

Это кэш **содержания сообщений**, а не только факта события: в encrypted record находятся текст, message id, время и connection id. Исходный webhook может содержать sender/recipient identifiers и номер отправителя WhatsApp; эти дополнительные поля обрабатываются в памяти и в текущий кэш не записываются. TTL считается от receivedAt: записи возрастом 30 дней и старше не выдаются при read, удаляются при startup lifecycle tick и каждом scheduled tick (по умолчанию минута), даже без новых webhook. Пока процесс остановлен, ciphertext может оставаться на диске до следующего startup sweep; expired content всё равно не обслуживается. Другие API read responses брокер не архивирует. Внешний AI-клиент получает данные только по явному выбору пользователя, автоматической передачи моделью по умолчанию нет.

## Проверенное удаление subject из рабочего хранилища

Это закрытая owner операция, без нового публичного MCP tool. Сначала оператор проверяет принадлежность аккаунта и согласует полный объём удаления всех Meta-подключений данного внутреннего subject. Email/публичный handle не подставляют вместо platform user id. Удаление одного subject не меняет данные другого.

1. Остановите конкретный service unit штатным SIGTERM и убедитесь, что процесс завершён. CLI использует тот же writer lock и откажет при живом процессе или stale lock; автоматического снятия lock нет.
2. В том же защищённом service environment задайте только `META_BROKER_STATE_DIR` и `META_BROKER_VAULT_KEY`. Secrets не передавайте аргументами и не печатайте. Указанный vault должен уже существовать: ошибочный путь не создаёт пустой «успешно очищенный» store.
3. Из checkout/install directory выполните `node dist/student/purge-subject.js --subject PLATFORM_INTERNAL_USER_ID --confirm-purge`. Параметр subject должен быть ровно проверенным внутренним ID. Команда удаляет его connections, grants/credentials, cached events, OAuth pending states и generation keys из Meta и YouTube vault; stdout содержит только суммарные числовые counts, stderr — безопасный error code. Vault очищаются отдельными транзакциями: при ошибке после первого commit повторите команду после устранения причины; повторное удаление безопасно. Отсутствие `--confirm-purge` даёт отказ. `vault_commit_uncertain` не считается успешным удалением: сначала восстановите filesystem и повторно проверьте состояние под offline lock.
4. Проверьте counts и выполните независимый read-back рабочего vault в закрытом контуре; только затем возобновите service. Старые callbacks после purge не имеют state. Последующее новое добровольное OAuth может создать новое подключение.
5. Отдельно обработайте backup/архивные ciphertext и копии у третьих сторон по согласованному запросу. CLI удаляет записи текущего рабочего vault; не обещает физическое стирание блоков filesystem, исходных данных Meta или всех внешних копий. Процедура не отправляет Meta-запросов или писем.

## Google channel discovery errors

Only an actual `youtubeSignupRequired` reason in a bounded, unambiguous Google error array from the fixed `https://www.googleapis.com/youtube/v3/channels` endpoint, with matching HTTP/body401, maps to fixed audit code `youtube_no_channel` and the existing `youtube=no_channel` callback. The existing UI asks the owner to choose an account with a YouTube channel; previously connected channels are preserved. `authorizationRequired`, absent/unknown/mixed reasons, token/userinfo endpoints and non-Google responses retain their existing authorization/error handling. HTTP401 alone does not establish that a channel is absent, and provider messages/contacts/payloads are never logged or returned.

Source: [YouTube Data API request-context errors](https://developers.google.com/youtube/data/reference/rest/v3/errors#request-context-errors). This classification does not establish the cause of an earlier live401 for which the provider reason was not captured; operator retry remains necessary.
